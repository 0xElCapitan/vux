## Learnings

- [Supply-chain technique — a vendoring framework severs the edge you would verify] When an advisory names package X and your lockfile has no edge to X because the framework vendors a compiled copy, both the dependency graph AND the framework's version number are proxies, not evidence. Verify the bytes: extract build stamps from the vendored tree, test them against a fix floor derived from the *publish dates* of the fixed releases, and fail closed on any stamp you cannot parse. The strongest available evidence is an **asymmetry** — stamp the packages the advisory says are NOT vulnerable too; if the vulnerable ones were rebuilt and the others were not, that split is a targeted security rebuild and independently corroborates the advisory's package scope (a wholesale bump moves all of them, a cosmetic change moves none). Also assert nothing resolvable at top level can shadow the vendored copy. State the limit in the tool's own output: vendored stamps are usually internal build identifiers not published to the registry, so no byte-comparison against a fixed release is possible. → `skills-pending/verifying-vendored-dependency-patches`
- [Provenance hygiene — a truncated search converts a lookup failure into a factual claim] `| head`, `-m N`, and result caps answer "absent from the first N", which is byte-identical in the output to "absent". When the claim being recorded IS an absence, that difference is the whole finding: a `head -6` over a 4,424-tag namespace put "no upstream tag exists" into an authority artifact for a tag that exists. Compounded by naming schemes changing across eras, so a probe validated on a recent release encodes an assumption that silently fails on an older one — the failure looked like a fact about the *version* when it was a fact about the *probe*. Enumerate fully, record the namespace size next to the finding, try every candidate scheme, and retract in place rather than silently editing. Complements [[proving-a-capability-is-absent]]: a positive control catches a *broken* search, not a correct-but-capped one. → `skills-pending/absence-claims-survive-truncation`
- [Security-testing precision — defining a capability is not using it] A grep-based gate over built output fires on `createServerReference`; the hit is the bundled runtime's own `t.createServerReference = function(…)`, shipped unconditionally, with zero materialised-product markers. Both available reflexes are wrong — deleting the check loses the only mechanical enforcement, and demanding the identifier be absent is unsatisfiable, so the check gets deleted later anyway. Sharpen the predicate instead: count definitions (`X [:=] function`) separately from uses, and assert the stronger signal (the type marker of the materialised product) alongside. Print the distinction in the tool output so a reviewer can calibrate a PASS, keep the reason in the source, and prove with a negative control that the sharpened check still fires on real use. Same family as [[selector-constants-are-shift-normalized]]: a substring search over compiled output answering a different question than the one asked. → `skills-pending/capability-definition-is-not-use`
